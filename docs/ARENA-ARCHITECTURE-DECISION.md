# 架构决策：角色进程运行原生 Mineflayer

日期：2026-10-18

状态：已决定；当前实现说明见 [目标架构](TARGET-ARCHITECTURE.md)，剩余工作只列在 [路线图](ROADMAP.md)。

## 决定

每个角色在参赛容器中运行一个常驻原生 Mineflayer 进程。参赛模块通过任务接口进入该进程，直接接收真实 bot 对象，并在本进程内读取状态、监听事件、调用 Mineflayer 方法和插件。一个角色只有一个游戏连接。

跨进程的 bot RPC 仅支持运行模块、取消任务、读取任务状态和读取会话状态。不得恢复本地 bot facade、状态或事件镜像、任意方法调用、远程事件代理或通用对象序列化。任务取消与退出负责释放移动控制；模块应处理取消信号并避免阻塞事件循环。

`bash`/`arena-task` 管理任务等待、取消和结果交付；`InboxClient` 将程序报告送回模型；可信会话和公开数据通过平台消息送达。世界记忆记录角色已经收到的区块，由模块在角色进程内查询。模型转发只传递模型 API 请求，不参与游戏或会话语义。详见 [上下文交付](CONTEXT-DELIVERY.md)。

身份入口只约束角色登录和网络可达范围。容器及其 Mineflayer 代码不可信，提示词和本地程序都不是公平性边界；游戏规则、计分、时间与行为限制由服务器数据包或插件执行。服务端默认原版，反作弊作为可选服务端配置，具体规则及验证状态见 [游戏模式](GAME-MODES.md) 和 [路线图](ROADMAP.md)。

## 原因

Mineflayer 的 world、entities、inventory、窗口、插件和事件本来就是进程内对象。把 bot 留在可信侧并将它们映射成远程对象，需要维护字段选择、同步查询、对象引用、回调和事件顺序，还会让 Pathfinder 等插件依赖一份行为近似但并不等同的镜像。原生进程复用 Mineflayer 自身语义，将平台间的交互压缩成少数任务操作，同时让完整 bot API 留在真正使用它的进程内。

这项选择把角色进程的可用性责任交给运行时：同步死循环可能阻塞角色，模块异常可能影响同进程任务。受管任务、取消信号、状态与外部进程监督用于发现和恢复这些故障，不声称模块能被本地 API 隔离。

## 公平与安全边界

参赛容器可修改代码并能构造 Minecraft 协议流量。因此角色进程、插件、本地工具和提示词都不作为可信的动作来源证明。入口负责角色身份、连接准入和网络隔离；服务器负责判定可接受的移动、交互和比赛结果。合法自动化及对服务器已发送信息的分析由比赛规则明确允许；违规行为由服务端规则处理。

采用原版服务端意味着它不提供与专用反作弊相同的行为检查。启用反作弊时，配置和处置方式必须随场次明确记录；仅记录不能被描述成阻止违规。比赛验证证据和当前限制集中在 [VALIDATION.md](VALIDATION.md)。
