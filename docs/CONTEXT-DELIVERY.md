# 模型上下文：来源与时机

本文写给要修改 Pi 扩展、后台模块或日志内容的开发者。它说明参赛模型在什么时候看到什么。参赛模型自己读到的说明在 [participant/agents.d/10-arena.md](../participant/agents.d/10-arena.md)；术语见 [README](../README.md)。

## 原则

游戏里发生的事不会自己进入模型的上下文。角色、程序和后台模块由工具包的 `mf` 运行，游戏信息追加进 `.mf/log/<来源>.jsonl`，只有模型运行 `mf log` 时才读出：从上次读到的位置起，每个来源一段，读时归纳（同 key 只留最新，连续重复合并，来源可以自带归纳，例如 explore 汇总成方块种类和数量）。Pi 扩展只管“命令”这一层：命令什么时候结束、结束了告诉模型，再加上可信侧的平台消息。

所以程序需要模型做决定时，应该**结束**并在返回值里说明原因：结束会送到模型那里，日志条目只会等模型来读。紧急条目只让正在等待的 `mf run` 提前返回 `running`，只带一行原因（来源和角色），内容仍在 `mf log` 里（程序继续跑，见下文）；没有 `mf run` 在等时，它只在日志里等。

## 请求边界

模型只在发出一次请求时读取上下文。两次请求之间，游戏和程序照常运行。本项目的 `bash`（带 `command` 启动任务，或带 `taskId` 接着等）在两种情况下返回：

- 命令结束：返回 `completed` 和输出。
- 等待时长用完（默认 30 秒，`wait_seconds` 或 `ARENA_TOOL_WAIT_SECONDS` 可改）：返回 `running` 和 `taskId`，**命令继续运行**。之后每次返回 `running` 只带上次返回之后的新输出。完整输出在任务目录的 `stdout.log`／`stderr.log`。

`mf run` 是一条普通命令：它一直等到程序结束，边运行边打印输出。`bash` 的任务被停掉时 `mf run` 这个客户端退出，程序本身继续在角色上跑；停程序要用 `mf cancel`。

Pi 在下面这些时刻发出请求：

| 请求边界                     | 例子                                                          |
| ---------------------------- | ------------------------------------------------------------- |
| 一条 prompt 开始一轮对话     | 启动器发出的开局提示；请求恢复发出的续写提示                  |
| 一批工具调用全部返回         | 同一条模型回复里的所有工具调用都返回后                        |
| 一轮结束时扩展要求继续       | `turn_end` 返回 `continue: true`                              |
| 扩展发出一条触发新一轮的消息 | 空闲时命令结束（`arena-tasks`）、空闲提醒、新通知（平台消息） |

## 什么时候送达什么

| 时机               | 内容                                                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 本身就是边界       | `bash` 返回；开局提示（会话简报、玩法说明、会话文件路径）                                                                                                    |
| 随下一次边界附带   | 没有等待者时结束的命令（`Finished tasks`，附在工具结果末尾或 `turn_end` 的历史记录里）；平台消息里变化了的 `session`／`public`／`notice`／`modelRate`        |
| 唤醒空闲的模型     | 空闲时结束的命令（包括因紧急条目提前返回的 `mf run`）；`public.notice` 变化；会话进行中且模型启动的命令都已结束 5 秒（`ARENA_IDLE_REMINDER_MS`）后的空闲提醒 |
| 只在模型查询时读取 | `mf log`：后台模块（默认 chat、danger）和程序写的条目，以及死亡、断线、维度变化、会话状态变化等“停止”（stop）；`mf snapshot`；`mf status`；任务日志；截图    |

“停止”（stop）就是数据里带 `stop: "原因"` 的日志条目，supervisor 自己写死亡、断线、维度变化、会话状态变化、进程崩溃或无响应这几种，程序也可以写。它会中断角色当前的程序（结果是 `interrupted` 和原因）。如果它没有出现在任何程序的结果里，该角色下一次 `mf run` 先打印 `[since your last run] stop: …` 再照常运行，不再拒绝运行。这保证模型不会在没看到死亡的情况下继续给角色下命令。

紧急条目（停止以外）只让正在等待的 `mf run` 立即返回 `running`，程序继续在后台跑：前台等待时模型马上看到；被 Pi 转到后台的 `mf run` 因此结束，等于唤醒模型。来源：danger 模块的危险血量、短时间大量掉血、近处风险（膨胀的苦力怕、点燃的 TNT、弹射物、正在瞄准的生物）和溺水；watchdog 模块（比赛默认不开）的同一处反复死亡；程序写的 `urgent` 条目；`ARENA_CHAT_WAKE` 匹配的聊天。

上下文被压缩后，扩展在下一次请求前补一条 `arena-after-compaction`：仍在运行的命令和一次 `mf log --all` 的输出（日志里保留的全部条目，已读未读都有，每段过长时只留最新部分；不移动已读位置）。

## 场外消息：两种接口

游戏以外的人或系统要对模型说话，有两种接口。两种最后都落在 harness（这里是 Pi）的输入上，区别是谁来写：

| 接口       | 谁来写                                                                         | 在本仓库里                                                                                                                                                                                                                                         |
| ---------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 直接接口   | 使用 harness 的人，通过 harness 自带的用户输入（Pi 的输入框，rpc 的 `prompt`／`steer`／`follow_up`） | 比赛里没有人接着 Pi。Pi 以 `--mode rpc` 运行，这条通道只有启动器在用：写开局提示和请求恢复的续写提示（[bootstrap.mjs](../packages/pi-extension/bootstrap.mjs)）。运营者不能借它给模型发话，这是有意的：比赛中不该有场外指导。在真机上用工具箱自己玩时，主要走这条。 |
| 自动化接口 | 可信侧的状态，由适配层转成 harness 的输入                                      | 数据包或运营者写 `arena:session`（`state`、`winner`、`public`、`public.notice`），Pi 扩展读会话后发平台消息（见下节）。运营者在比赛中要对模型说话，就写 `public.notice`，例如 `node packages/arena/src/cli.mjs command 'data modify storage arena:session public.notice set value "..."'`。 |

下面这些不是场外消息：

- 游戏聊天，包括运营者用 `arena command say`／`tell` 发的。它是游戏内容，任何玩家都能发同样的话；默认聊天模块把它标成 `trusted: false`，模型按游戏数据看待，不当作指令。
- `mf` 收件箱。它的 socket 在参赛容器里，模型自己的程序也能往里写，承载不了信任。不要给它加可信侧的投递接口，可信消息只走平台消息。

没有规则数据包的 `open` 会话两种接口都没有：没有人接着 Pi，`public` 恒为空。补法记在 [路线图](ROADMAP.md)。

## 平台消息

平台消息不进游戏日志。`turn_end` 时扩展通过只读 `session` 接口读取会话状态（缓存 2 秒，超时 300 ms），`kind`、`sessionId`、`state` 或 `winner` 有变化时组成带 `session` 段的平台消息，用 `triggerTurn: false` 交给 Pi。不报已用时间和剩余时间：时限由服务器上的规则执行，模型不知道。

`public` 段：开局提示里的 `briefing.public` 是基线，之后它一变，下一条平台消息就带 `public`（JSON 超过 4096 字节时只报大小和 `public.json` 的路径）。`public.notice` 变化时另带 `notice` 段（超过 2000 字符截断）。Pi 空闲时扩展每 `ARENA_NOTICE_POLL_MS`（2000 ms）读一次会话，通知一变就用 `triggerTurn: true` 发一条平台消息开启新一轮。

所有来自可信侧的消息都由 `index.mjs` 的 `deliverPlatform` 发出，以 `Arena platform message` 开头。

## 默认收集与默认交付

| 能力                          | 默认收集                          | 交给模型                                                    |
| ----------------------------- | --------------------------------- | ----------------------------------------------------------- |
| 聊天（chat）                  | 是                                | 进 `mf log`，一行一条；`ARENA_CHAT_WAKE` 让匹配的聊天变紧急 |
| 危险（danger）                | 是，每秒采样                      | 进 `mf log`；受伤、近处风险、饥饿、缺氧；严重的为紧急       |
| 自身状态                      | 否                                | 模型用 `mf status`／`mf snapshot` 或程序里读                |
| radar、explore、watchdog 模块 | 否，模型用 `mf run --keep` 打开时 | 进 `mf log`；explore 读时汇总成方块种类和数量               |
| 程序内看门狗                  | 控制型程序默认开                  | 写进该程序自己的输出（`[watchdog] …`）                      |
| 图像                          | 否，运行截图脚本时才生成          | 模型用 `read` 读截图脚本写出的 PNG                          |
| 区块记忆                      | 运营方打开时，在角色进程中        | 不交付，模块查询时才读                                      |
| 平台消息                      | 是                                | 只发变化部分，随下一次请求附带；通知会唤醒                  |

默认收集只花机器资源；模型读日志才占上下文。新增或修改一个模块时，回答：读时归纳会不会漏掉影响行动的短时信息；来回走、原地不动时会不会反复写同样的条目；需要模型马上处理的事，是否应该由程序结束来表达，而不是一个紧急条目。

## 已退役的方案

“每次请求都附上最新观察”的请求尾部方案、收件箱自动注入和收件箱本身（2026-10-24 改成日志）都已删除；紧急条目现在只让正在等待的 `mf run` 提前返回。前者的机制和放弃理由见 [实验记录](history/EXPERIMENTS.md)。
