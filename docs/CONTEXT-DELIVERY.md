# 模型上下文：来源与时机

本文写给要修改 Pi 扩展、默认脚本或自动报告内容的开发者。它说明参赛模型在什么时候看到什么。参赛模型自己读到的说明在 [examples/PROMPT.md](../examples/PROMPT.md)；术语见 [README](../README.md)。

## 请求边界

模型只在发出一次请求时读取上下文。两次请求之间，游戏和程序照常运行，模型看不到任何新东西。发出请求的时刻叫**请求边界**，新信息只能在这里进入上下文。

代理不会每来一行输出就调用一次模型：每次调用都要花预算、排队，还会把上下文塞满。所以工具调用会先等待，有结果再返回。本项目的 `bash` 和 `task_wait` 在两种情况下返回：

- 进程结束：返回 `completed` 和输出。
- 等待时长用完（默认 30 秒，`wait_seconds` 或 `ARENA_TOOL_WAIT_SECONDS` 可改）：返回 `running` 和 `taskId`，**进程继续运行**。模型之后用 `task_wait` 接着等，或用 `task_cancel` 停掉。

Pi 原生的 `bash` 不是这样：它一直阻塞到命令结束，超时或中止时杀掉进程。本项目把“这次等多久”和“进程活多久”分开：`timeout` 是单独的终止期限，中止一次工具调用只让它不再等待，不会结束进程。

Pi 在下面这些时刻发出请求：

| 请求边界                     | 例子                                                                               |
| ---------------------------- | ---------------------------------------------------------------------------------- |
| 一条 prompt 开始一轮对话     | 启动器发出的开局提示；请求恢复发出的续写提示；启动器在角色进入赛道时发出的赛道图像 |
| 一批工具调用全部返回         | 同一条模型回复里的所有工具调用都返回后，Pi 才发下一次请求                          |
| 一轮结束时扩展要求继续       | `turn_end` 返回 `continue: true`                                                   |
| 扩展发出一条触发新一轮的消息 | 空闲时的紧急唤醒（`arena-inbox`）、空闲提醒（`arena-continue`）                    |

## 来源与时机

信息有三个来源：

- **工具结果**：模型自己调用的工具返回的内容。
- **收件箱**：参赛者程序（包括默认脚本）通过 `InboxClient` 发来的消息，以及 Pi 扩展自己发的运行时报告。
- **平台**：可信侧和启动器发来的内容，包括会话时钟（来自比赛主控，独立运行时来自游戏桥）、预算网关的预算反馈、开局提示和图像。

相对请求边界，信息有四种到达方式：

| 时机                 | 工具结果                                                                                                                                                   | 收件箱                                                                                                                                                                                                                                                                           | 平台                                                                           |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **本身就是边界**     | `bash`／`task_wait` 返回 `completed` 或 `running`；`task_cancel` 返回 `cancelling`                                                                         | 无（收件箱不单独构成边界）                                                                                                                                                                                                                                                       | 开局提示（会话简报、玩法说明、开局图像、观察器第一份报告）；请求恢复的续写提示 |
| **随下一次边界附带** | 无                                                                                                                                                         | 默认观察器的 `observation.snapshot`／`observation.changed`、沿途方块报告、附近告示牌、普通事件；默认聊天转发的 `game.chat`；程序的 `post`／`upsert`；运行时报告 `runtime.snapshot`／`runtime.changed`（含程序自报状态 `programStatus`）；没有等待者时完成的任务 `task.completed` | 平台消息 `Arena platform message`：只含变化了的 `clock`／`budget`              |
| **提前制造边界**     | 无                                                                                                                                                         | 紧急消息：默认观察器的生命危急（`critical_health`，生命 ≤ 6）、短时大量掉血、死亡、断线；程序的 `requestJudgment`；设置了 `ARENA_CHAT_WAKE` 时提到 bot 或私聊 bot 的聊天。持续会话中，空闲时到达的 `task.completed` 也会唤醒模型                                                 | 空闲提醒；赛道图像（空闲时开启新一轮，忙时排在当前工具批次之后）               |
| **只在查询时读取**   | `observe`（`fullRuntime` 等参数展开明细）；截图脚本 `examples/screenshot.mjs`；程序里用 `createBlockMemoryClient()` 查询区块记忆；读程序自己写的日志或文件 | 无                                                                                                                                                                                                                                                                               | 无                                                                             |

同一次工具返回可以同时带有工具自己的结果和附带的收件箱消息。“只在查询时读取”的数据最终也通过一次工具结果进入上下文，区别在于模型主动要了它。

## 每个边界做什么

“排空收件箱”指取出所有已到交付时间的消息，一次交给模型，并把它们标记为已送达。程序可以用 `InboxClient.delivery(id)` 得到送达回执。没到交付时间的消息（例如沿途方块报告首次排队后至少 30 秒才可交付，见 `ARENA_OBSERVER_RECENT_BLOCK_MIN_REPORT_MS`）留在队列里，等下一个边界。同一来源、同一 key 的可替换报告会替换还没送达的旧版本。

| 钩子                 | 何时触发                                                                                                       | 做什么                                                                                                                                                                                                                                                  |
| -------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `before_agent_start` | 每条 prompt（开局提示、续写提示、赛道图像）开始一轮之前；扩展自己发的 `arena-inbox`、`arena-continue` 不经过它 | 第一次时等默认观察器的第一份报告，最多 `ARENA_OBSERVER_READY_MS`（5000 ms）；生成运行时报告；排空收件箱。三者和收件箱用法说明一起放进一条 `arena-inbox-setup` 消息                                                                                      |
| `tool_result`        | 每个顶层工具返回时                                                                                             | 重新计算运行时报告，有变化就入队；收件箱里有可交付消息时排空，追加到这个工具结果的末尾。嵌套工具结果（带 `parentToolCallId`，例如 codemode 中代码调用的工具；codemode 是 Pi 让模型写代码来调用工具的模式，默认关闭）跳过，由外层工具结果交付            |
| `turn_end`           | 每轮结束时                                                                                                     | 清除紧急释放状态，之后的等待重新正常阻塞；发送平台消息；把剩余可交付消息排空成一条 `arena-inbox` 历史记录。如果这一轮没有工具调用（模型给出了最终回复）、没有中止或出错、比赛没结束，且这批消息里有需要模型决定的消息，就返回 `continue: true` 再跑一轮 |
| 空闲唤醒             | Pi 空闲时有消息入队，或一次运行刚结束（未中止）时                                                              | 比赛未结束、Pi 没有排队的消息，且队列里有需要模型决定的消息时，排空整个队列，用 `triggerTurn: true` 发一条 `arena-inbox` 消息开启新一轮                                                                                                                 |
| 空闲提醒             | 持续会话中，模型正常停下 `ARENA_IDLE_REMINDER_MS`（5000 ms）后                                                 | 只有在 Pi 没有排队的轮次、没有非后台任务在运行、可信侧报告会话进行中（比赛或 `open` 会话）时才发。排空收件箱，和续跑提示一起放进 `arena-continue` 消息                                                                                                  |

“需要模型决定的消息”有两种：设置了 `ARENA_WAKE_ON_URGENT=1` 时的紧急消息（持续会话中启动器默认设为 1），以及持续会话中运行时发出的 `task.completed`。其他普通消息在空闲时只排队，不唤醒模型。默认脚本是后台任务，它们在运行不会挡住空闲提醒；参赛者自己的任务在运行时，空闲提醒不发，等任务完成或紧急消息来决定下一次请求。

运行时报告只在 `before_agent_start` 和顶层 `tool_result` 计算。程序用 `setStatus` 更新的自报状态因此在下一次顶层工具返回时才出现在 `programStatus` 里。

## 平台消息何时送达

平台消息不进收件箱。`turn_end` 时 Pi 扩展通过游戏桥的 `/v1/session` 读取会话状态（缓存 2 秒，超时 300 ms），并取出预算网关在模型响应头里给出的预算（请求被限速拒绝时改读网关的 `/budget`），只把变化的部分组成一条 `arena-platform` 消息，用 `triggerTurn: false` 交给 Pi。会话进行中的时间按 10 秒分档去重；会话状态或胜者一变，下一次 `turn_end` 就会发出。`open` 会话没有时限，时钟只报已运行时长（`elapsedMs`），不报 `durationMs`／`remainingMs`。

`triggerTurn: false` 在 Pi 里的效果：一轮还在运行时，消息先暂存，等这一轮的工具结果都写进历史后再追加，所以它不会插在工具调用和工具结果之间；不在运行时直接追加。它自己从不发起请求。如果这一轮还会继续，它随下一次请求送达；如果这是最终回复，它留在历史里，等下一次不论由谁触发的请求。

## 紧急消息能做什么

模型正在等待时，一条紧急消息的经过：

1. 程序用 `requestJudgment` 或 `priority: "urgent"` 发消息。
2. 任务管理器让所有受管的 `bash`／`task_wait` 等待立刻返回 `running`，原因写明是哪条紧急消息。同一批里随后才开始的等待也立刻返回，直到这一轮结束。进程都继续运行。
3. 这批工具全部返回，`tool_result` 排空收件箱，紧急消息随工具结果送达，Pi 发出下一次请求。
4. 模型决定继续 `task_wait`、改程序或 `task_cancel`。程序的最终输出只交付一次：要么在某次 `task_wait` 的结果里，要么在没有等待者时作为 `task.completed` 消息。之后再等同一个 `taskId` 只得到一个 `delivered` 回执。

模型空闲时，紧急消息通过上面的空闲唤醒开启新一轮。

紧急消息做不到的事：

- 打断正在生成中的模型回复。
- 释放受管等待以外的等待，例如 codemode 里的长时间计算或其他工具的网络等待。
- 插进当前工具批次中间：它总要等这一批工具全部返回后才送达。

## 一次导航的例子

模型运行一个导航程序，`bash` 等了 30 秒后返回 `running` 和 `taskId`，附带这段时间里默认观察器报告的位置和物品变化。模型调用 `task_wait` 继续等。途中经过的方块类型累计成沿途方块报告，最早 30 秒后随某次工具返回送达；附近告示牌的文字也随下一次返回送达。游戏桥同时记录角色收到的区块，以后模型可以在程序里查询已经卸载的位置，得到的是最后收到的历史。

途中生命降到 6，默认观察器发出紧急消息。`task_wait` 立刻返回 `running`，模型马上得到一次请求，导航程序继续跑。模型可以接着等，也可以取消导航去吃东西。

## 默认收集与默认交付

“默认收集”和“默认交付”是两个独立的选择。

| 能力         | 默认收集                                     | 默认交给模型                                                                     |
| ------------ | -------------------------------------------- | -------------------------------------------------------------------------------- |
| 默认观察器   | 是，每秒采样（`ARENA_OBSERVER_INTERVAL_MS`） | 变化随下一次边界附带；危险事件作为紧急消息提前送达                               |
| 沿途方块报告 | 是，每秒采样                                 | 汇总后最早 30 秒送达一次；逐格数据留给查询                                       |
| 默认聊天转发 | 是                                           | 默认随下一次边界附带；配置 `ARENA_CHAT_WAKE` 后，匹配的聊天作为紧急消息唤醒空闲模型 |
| 开局图像     | 只按地图配置生成                             | 开局提示带一张；开局时角色在大厅的，进入赛道后再发一张赛道图。其他图像靠截图脚本 |
| 区块记忆     | 是，在游戏桥上                               | 不交付，程序查询时才读                                                           |
| 运行时报告   | 是                                           | 只发变化部分，在顶层工具返回时附带                                               |
| 平台消息     | 是                                           | 只发变化部分，随下一次请求附带                                                   |

默认收集只花机器资源；默认交付会占用模型的上下文和注意力；提前交付还会多花一次模型调用并打断原计划。所以一项信息越往后一级，越需要理由。一项能力适合默认收集，不代表它适合默认交付。

## 默认报告要回答的问题

新增或修改一项默认报告时，回答这三个问题：

- **漏掉与迟到**：汇总会不会漏掉影响行动的短时信息？等到下一次边界再送是否还来得及？来不及的要走紧急消息。
- **重复与开销**：在同一区域来回走、原地不动、几份报告说同一件事时，会不会反复占用上下文？保存原始数据和发送摘要可以分开调整。
- **打断的价值**：提前判断能不能留下有效的反应时间？收益是否超过多一次模型调用和打断原计划的代价？普通进度随下一次边界附带即可。

哪些默认项已在真实比赛中验证，见 [验证](VALIDATION.md)；还没验证的列在 [路线图](ROADMAP.md) 的“待实战验证”。
