# 模型上下文：信息来源、交付时机与默认选择

后台能力解决“哪些信息已经收集、以后能回答什么”，交付机制解决“模型何时看到哪些内容”。两者分别选择，入口文档负责告诉玩家现有数据和读取入口。

## 所属层次与默认行为

比赛宿主、受限 Minecraft Bot 接口、模型预算、后台任务生命周期与 Inbox 是运行框架；Pi 负责当前框架的 Agent 会话接线。**态势感知、世界视觉、区块记忆都是可复用的预装工具箱能力**，并不因为某项需要自动启动、在可信侧保存数据或需要 Pi 呈递结果，就成为新的框架层。

三项工具箱的默认政策不同：态势感知默认监听并选择性向模型报告，世界视觉只按地图配置提供开局图像、其他时候按需渲染，区块记忆默认收集但通常只在代码主动查询时读出。Skill 介绍调用与修改入口：默认观察器和聊天监听是开局自动启动的普通脚本（受管后台任务），通过 `InboxClient` 和送达回执交付，可停掉或换成自己的版本；Pi 只负责启动它们，以及平台消息和运行时状态；区块记忆由可信 Bridge 初始化，可由宿主替换或关闭。[框架与工具箱分类](../README.md#框架预装工具箱与-skill) · [工作清单](PERCEPTION-TODO.md)。

## 四类信息进入上下文的方式

| 方式 | 来源与时机 | 例子 |
| --- | --- | --- |
| 主动执行的预期返回 | 模型主动调用工具或脚本，本次操作按原有返回约定给出结果 | 启动导航后收到运行状态、输出和最终结果；一次 `observe` 返回所选状态 |
| 后台收集，按需读取 | 程序或服务先持续收集、保存，模型有问题时再读取 | 查看后台程序日志；通过共享方块记忆查某坐标或此前收到的区块 |
| 普通 Inbox 合并 | 后台选中的普通信息合并到下一工具返回，保留会话历史 | 沿途方块区间、附近牌文字变化、程序进度与动作经过 |
| 更早判断（early） | 事件值得比原等待结束更早判断，提前释放等待或唤醒空闲会话 | 危急生命、死亡、程序的 `requestJudgment` |

这些区别关注来源和交付预期。同一个工具结果可以同时包含主动操作的结果和附带的 Inbox；读取后台记忆也通过普通工具完成。详细队列与等待语义见 [Inbox](../packages/inbox/README.md) 和 [Pi 集成](../packages/pi-extension/README.md#behavior)。

## 默认收集与默认交付是两个维度

共享区块记忆在桥服务中默认记录角色实际收到的完整区块，卸载后保留历史。它让后续脚本回答“以前这里是什么方块”“牌上写了什么”等问题，使用 `createBlockMemoryClient()` 查询。默认收集承担存储和维护成本；数据在模型主动读取时进入上下文。后台日志同理，保存内容和保留期由相应程序决定。

近距摘要则同时默认采样和默认报告：每秒采样透明连通空间，持续更新同 key 的完整累计结果，首次待交付起至少 30 秒后进入普通 Inbox 交付边界。它以较小报告提示沿途出现的类型、少量代表坐标和空间覆盖；精确逐格数据、完整区块与更详细的采样记录由按需入口提供。采样频率、保存范围、报告内容、交付延迟分别决定成本和覆盖。

默认启用是项目最强的推荐，比文档里的“可以用”或“适用时先试”承担更多责任。默认收集表示项目愿意常态支付相应资源成本；默认交付还表示项目认为这类信息值得常态占用模型注意力。early 进一步占用判断时机和新的模型调用。一个能力适合默认收集，仍可只供按需读取。

## 用一次导航看交付边界

模型启动导航，本来就预期收到位置、运行状态和结果，这是主动操作的返回。导航途中，桥继续保存收到的区块；以后查一处已经卸载的位置时，读取这份后台记忆；如果该列卸载后世界又变化，返回的是最后收到的历史而非实时保证。沿途摘要和附近牌变化进入 Inbox；下一次工具返回附带已满足交付条件的内容。方块摘要若尚未达到最小间隔，继续累计到之后的交付边界。

若途中出现危急生命，early 让受管等待提前返回，模型提早获得新的判断机会，导航程序仍按自身代码运行。模型随后选择继续等待或取消。原操作的完成结果沿实际 `task_wait` 或完成事件交付一次，见 [进程结果语义](../packages/inbox/README.md#core-process-api)。

## 默认信息选择的责任

默认项要依据它改变了什么决定、避免了什么漏失来取舍。主动请求的结果已有明确需求；后台自动交付则由项目替模型选择注意力，应同时承担以下后果：

- **漏失与迟到：** 汇总是否遗漏会影响行动的短时信息；延迟到下一边界是否还来得及。近距每秒采样和延迟交付各有覆盖边界，危急事件另走 early。
- **重复与开销：** 同一区域反复经过、静止采样、多个报告描述同一件事，是否增加上下文和判断负担。保存原数据与发送摘要可以分别调整。
- **打断的价值：** 提前判断能否留下有效反应时间，收益是否超过额外模型调用和原计划被打断的代价。普通进度合并交付，值得更早判断的情况走 early。

实现存在、接口测试通过、实际使用有效是不同证据。当前区间合并与交付水位有自动化覆盖；新雷达、完整区块记忆及报告取舍的实际比赛效果继续见[验证记录](VALIDATION.md)和[工作清单](PERCEPTION-TODO.md)。这些证据用于调整默认项、报告范围与时机。

## 当前实现与设计边界

- 开局提供基础观察；开局及新的外部 prompt 入口、顶层工具结果取样状态变化。`turn_end` 还会把剩余普通 Inbox 写入历史，供下一自然请求读取，自身不触发模型调用。
- 默认 early 条件包括危急生命、显著／连续伤害阈值、死亡和实际 `end`／`kicked`。雷达、聊天、方块和牌使用普通 Inbox。程序另可显式调用 `requestJudgment`。
- 忙时 early 已接入受管 `bash`／`task_wait` 的等待释放，原程序继续运行；常驻空闲会话可由紧急事件或程序完成唤醒。概念上的 early 也可由及时 steer 实现；当前 Pi 的 steer 在工具批次中仍排队，默认套组没有立即中止模型生成的实现。任意网络等待或持续 codemode 计算的更早释放也尚无通用机制。
- `publishCurrent` 维护有时效的当前值，供后续 `programStatus` 观察读取；值的更新、过期和清除通过普通状态交付体现。它属于后台保存与既有交付路径的组合。

无运行任务时的五秒续跑与模型错误恢复负责维持会话运行，沿既有上下文继续执行。
