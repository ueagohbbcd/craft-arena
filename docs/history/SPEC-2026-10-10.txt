Craft Arena 项目规格

需求与架构基线 0.1　｜　2026 年 10 月 10 日

Craft Arena 给通用 coding AI 一个可编程的 Minecraft 角色，让它在公开能力和有限资源下自由竞争。参赛者围绕地图目标观察、决策、编程和执行；测试场按游戏进展、胜负、模型用量与墙钟时间，比较决策和编程效率。首类场景是 Race of Wool 一类 PvP 竞速地图。

阅读与实施状态

本文保留首版需求与架构设计基线，并在关键接口处补充当前实现。阅读时先用本页了解交付范围，再按正文追溯设计；部署步骤、接口用法和验证结论以随包现行文档为准。

角色与自由编程：一个参赛容器配置主 agent 和游戏 bot。agent 可逐步操作，也可运行普通程序、事件与长期行为，自行组织子代理模型程序；调用统一走预算网关。

游戏能力：有限 Mineflayer 风格接口、同步世界镜像、语义动作、聊天、选定 Pathfinder/PvP 适配、自定义 Goal/Movements，以及俯视图和 3D 观察材料。

持续比赛：常驻 Pi（resident Pi）保留同一会话；普通消息在返回边界交付，紧急消息请求提前判断，程序可继续运行。等待、完成交付和显式取消各有独立语义。

资源与协作：按官方 API 报价折算的个人与队伍现金速率窗口、排队和比例反馈，与游戏墙钟共同约束决策；队内 Git 共享代码和资料，游戏聊天用于协作。可信宿主管理开局、目标计分和结束。

核心回路已有集成测试：真实 Pi、选定插件与普通进程已接入，游戏状态使用可控夹具，模型使用固定假上游。现金速率与比例反馈的新增验证，以 docs/VALIDATION.md 和 docs/INTEGRATION.md 的最新记录为准。

配置与部署验收：运营者提供地图、服务器、目标规则及模型服务，在目标主机验收隔离、Unix socket、真实材质截图和真实对局。插件实战、资源计量与统一能力配置随选图复核。后续实验：多地图扩展及启发式反馈。

阅读导航：README.md 看项目入口；docs/FEATURES.md 看完整特性与状态；docs/PLAYER.md 看参赛者操作；infra/README.md 看部署。模块 README 给出精确接口和兼容差异，docs/VALIDATION.md 记录已验证范围与剩余验收。

1 目标与设计边界

1.1 要比较的能力

游戏理解与决策：识别胜利条件，判断路线、资源、战斗和队内分工，依据局势调整。

程序化执行：把重复动作和可判断的条件交给代码，合理使用插件、自定义 Goal、事件和持久状态。

有限模型调用速率下的取舍：决定哪些状态需要看、哪些事件需要汇总、何时需要模型重新判断，并承担决策延迟的游戏后果。

手动逐次操作与程序化操作都是合法参赛方式。平台提供玩家行动能力和编程材料。采集、施工、自动吃饭、战斗与队伍协作的组织方式由参赛者决定。

1.2 规格状态

以下状态用语保留设计基线语境；当前实施状态先看首页导航和验证报告。“确定方向”表示已选择的产品与架构方向；“建议默认”是便于原型推进的起点，可经测试调整；“待验证”需要原型或实测支持；“待决策”须在正式比赛配置冻结前明确。下文“应”指首版目标，“可”表示参赛代码或平台的可选能力。源码观察单独标明来源，产品范围以规格和验收结论为准。

能力边界以统一、公示为原则。Mineflayer 能提供比原版客户端更强的信息和操作能力；允许将 X-ray 式方块信息、快速搭建等纳入比赛能力配置。参赛程序通过统一的语义操作行动，任意 Minecraft 协议发包权限保留在可信后端。具体信息范围、动作速率与可用插件版本仍需冻结。

2 比赛组织与完整流程

2.1 参赛单位与协作

确定方向：一个容器对应一个主 agent 和一个 bot；队伍可由多个参赛单位组成，人数和匹配方式待定。参赛代码可自行组织调用模型的普通程序作为子代理，与主 agent 共用网关身份并纳入约定计量和限速。对子代理共享同一个游戏角色产生的并发操作，由参赛代码自行协调；平台可提供小型基础帮助。

队内 Git 用来共享代码、资料和固定版本插件源码；其他交流通过游戏聊天完成。赛前可用资料、赛中 Git 的可见范围与更新规则、外部网络准入、是否允许跨队仓库及赛后保留内容，需要写入比赛配置。Minecraft 连接统一经过可信后端。

2.2 生命周期

阶段 | 建议默认行为 | 需固定的输入或结果

准备 | 创建隔离运行环境，分配 bot 身份，装载工具与插件材料，检查模型网关和游戏桥接。 | 地图版本、环境镜像、队伍、模型速率配置、网络与资料规则。

开局 | 重置地图与角色状态，提供一次起始任务和规则说明，同时开始墙钟计时。 | 出生点、初始背包、计时起点及开局同步方式。

进行 | 模型判断、工具执行、结果交付持续循环；普通脚本和插件可在模型等待时继续运行。 | 实时状态、允许动作、剩余时间、速率比例反馈和可核实的异常。

结束 | 可信裁判依据地图目标、超时或其他已公布条件终止比赛，停止后续有效操作。 | 胜负或未决原因、终止时间、最终目标状态。

结果 | 生成对局结果及核心指标，保存足以复核异常和评分的日志。 | 胜负、游戏进度、资源消耗、异常与版本标识。



胜负首先服从所选地图的规则。例如羊毛获取、放置位置、有效顺序、队伍获胜条件，须以该地图的正式配置为准。死亡、重生、掉线、无操作、超时、平局、地图故障和重赛条件由可信裁判按赛前规则处理。建议首版先固定一张地图和一套规则，跑通全场，再扩展地图族。

比赛持续依靠“模型判断 → 工具 → 返回结果 → 模型判断”的回路运行。当前启动入口默认使用常驻 Pi RPC 会话，提交一次开局任务；紧急投递可继续同一会话，可信比赛结束或运营者终止时清理进程。成本占比、超速比例、排队与墙钟提醒属于比赛上下文，可用 user-role steer 或受控注入承载，与当前比赛任务一起进入上下文。

3 执行架构与可信边界

3.1 最小组件划分

位置 | 组件 | 职责

参赛容器 | Pi 与扩展 | 主 agent 会话、工具调用、消息收集与返回边界集成。

参赛容器 | 普通 Node 游戏进程 | 参赛代码、Pathfinder 与 PvP 插件、自定义 Goal 与 Movements、本地 bot facade 及状态镜像。

容器外 | 可信游戏后端 | 真实 Mineflayer bot、physics 与协议连接，校验并执行获准语义操作，发出状态事件。

容器外 | 模型网关与裁判 | 持有真实模型凭证，计量和限制调用，确认比赛状态与评分。



主 agent 与插件在同一容器，通常是不同进程。插件、用户定义的 Goal、Movements 及其同步回调在同一普通 JavaScript 运行时执行；参赛代码持有本地 facade，真实 bot 留在后端。

边界关系：Pi 调用容器内普通程序；程序通过本地 facade 读取世界镜像并调用获准游戏动作；动作及后端事件通过 stdio 或 HTTP 桥接到可信游戏后端；只有后端连接 Minecraft 服务器。程序另外通过本地 IPC 向 Pi 扩展投递需要模型看到的信息。游戏桥接和模型消息通道的用途不同。

3.2 能力隔离与主机安全分别成立

游戏能力边界限制的是参赛者能向服务器表达哪些动作。即使参赛者可阅读、修改插件源码，也只能通过公开的语义操作影响比赛。容器对 Minecraft 服务器的直连和任意协议代理应在容器外阻断。边界由网络准入与可信后端共同执行。

宿主操作系统与容器隔离解决的是另一层安全问题。文件、进程、CPU、内存、网络和凭证隔离按运行环境设置。真实模型凭证、权威配额和评分状态保留在可信服务内，并由该服务执行约束。

建议首版聚焦后端动作校验、连接准入与日志。队伍 Git、模型网关和必要资料访问的网络规则独立列明，保留正常编程所需的能力。

4 游戏接口与插件兼容

4.1 从实际插件需要反推接口

确定方向：提供 Mineflayer 风格的有限 bot facade。先盘点选定 Pathfinder、PvP 版本真正读取的字段、调用的方法及订阅的事件，再补充聊天、合成、容器交互和视觉等完整玩家任务需要。接口清单、行为差异与补丁随版本提供。

同步查询、搜索和回调读取本地镜像，整个寻路搜索在本地执行。镜像至少支撑选定插件使用的方块与区块、实体、角色状态、背包和物品信息。事件附带顺序或时间信息，便于发现延迟和过期；尚未到达的区块明确表示为未知。镜像覆盖范围和信息可见性由能力配置决定。

能力组 | 首版需覆盖的用途 | 关键约束

观察与查询 | 位置、生命与饥饿、装备、背包、附近实体、方块、地图目标及聊天。 | 同步本地读取；注明未知或过期状态。

基础行动 | 移动控制、朝向、跳跃、挖掘、放置、攻击、物品使用与装备。 | 由可信后端执行；动作完成与失败有清晰结果。

玩家交互 | 游戏聊天、合成、打开容器、取放物品及比赛所需交互。 | 按选图和插件实际需求确定首版清单。

插件扩展 | 加载选定插件、定义 Goal 和 Movements、使用事件与 Promise。 | 用户代码保留普通 JS 行为；适配差异公开。

视觉 | 快速大面积俯视小地图、Mineflayer 3D 视图。 | 返回裸图和独立说明；与状态快照可关联。



桥接消息建议统一采用 requestId 与协议版本。请求承载 action 和 args；结果对应 requestId，包含成功值或结构化错误；状态事件包含 sequence、时间与增量。容器内按实体与区块标识更新镜像。动作名和错误码由实际能力清单生成，协议仅表达获准语义操作。

4.2 已知兼容风险

源码观察：Mineflayer 原生插件加载器将真实 bot 传给插件。真实 bot 包含协议客户端等能力，因此本项目将容器内插件加载到有限 facade，并在外部后端保留真实 bot。[S4]

Pathfinder 的 fullStop 等路径会直接修改实体速度和位置；仅拦截方法调用不足以得到正确语义。建议为选定版本增加明确 stop 动作或小型兼容补丁，并实测站立、跳跃、挖掘和停止时的结果。PvP 持有并比较实体对象引用，镜像更新需要保留实体对象 identity，以就地更新支持持续目标引用。[S5][S6]

physicsTick 的时序、事件顺序、跨进程延迟、后端纠正和插件内部物理假设均待验证。应先验证选定插件及自定义扩展的典型路径，再声明具体兼容范围。兼容清单应列出已测路径、所需适配和已知异常。

插件源码和依赖版本对参赛者可见，并与运行环境一致。Pi 的核查及接入版本为 v1.1.0；当前交付已锁定 npm 依赖，包含 Pathfinder 2.4.5 和 PvP 1.3.2，Minecraft、地图与服务端版本由运营者配置并冻结。冻结后应记录版本和补丁，避免因依赖变化改变比赛能力。

5 Pi 工具回路与消息收件箱

当前设计区分主动执行的预期返回、后台收集后按需读取、普通 Inbox 随工具返回合并、以及更早判断（early）。后台采集和自动交付分别选择；默认项的推荐强度、资源开销和漏失责任详见 docs/CONTEXT-DELIVERY.md。

5.1 现成能力与需要补齐的部分

当前按 Pi 设计，默认直接使用普通工具；bash 启动普通操作系统程序，常驻游戏代码放在普通 Node 进程中运行。codemode 默认关闭；用户显式选择工具的 CLI 参数仍原样传给 Pi，其嵌套调用兼容测试保留。[S1]

原生 Pi v1.1.0 的 bash 以子进程退出等执行状态判断完成，不以终端提示符为结束标志。onUpdate 用于界面或扩展更新，不会定期唤醒模型。steer 会排队，需等当前 assistant 的整批工具完成才进入下一次模型调用；Esc 或 abort 可停止 bash 执行。本项目需要在这些现成行为之上实现等待提前返回。[S2][S3]

5.2 收件箱的消息交付职责

确定方向：把收件箱做成 Pi 扩展与集成工具能力，由集成层自动处理消息返回边界。参赛代码通过显式投递接口决定哪些信息进入收件箱，哪些覆盖旧状态，哪些不报告，以及何时请求模型提前判断。投递策略由模型和参赛代码选择。

当前通道：容器内脚本或插件 → SDK 或 CLI → Pi 扩展拥有的单个 /messages 服务。Unix domain socket 为默认入口，带身份验证的 loopback HTTP 为备选；扩展将连接配置传给受管子进程。stdio 适合已经建立的固定父子进程协议，任意进程向扩展投递时使用独立 IPC 入口。游戏权限仍由游戏桥接控制。

接口语义 | 最小输入 | 交付意图

追加事件 | 消息内容；可选来源、事件标识与时间。 | 保留有意义的离散事实，在下一返回边界一起交付。

按 key 更新状态 | key、最新内容；可选有效期。 | 同 key 只保留最新状态，避免重复刷屏。

请求提前判断 | 原因；可选关联任务及必要状态。 | 请求提前结束当前等待，让模型尽快看到原因。



当前 SDK 用 post、upsert 和 requestJudgment 分别表达以上三种语义；精确调用格式见 packages/inbox/README.md。模型可自由选择消息含义与聚合方式；扩展自动交付临时缓存，按容量、过期和摘要规则管理。状态过期后丢弃，原始大日志、地图数据与图像按需另存。容量溢出或摘要截断应可见，避免静默丢失关键事实。

当前 IPC 请求包含 sessionId、kind 和 data，可带 key、priority、ttlMs；kind 为 event、state 或 judgment。post 追加事件，upsert 按 key 更新状态，requestJudgment 投递紧急判断请求。接收端生成消息标识并确定来源。消息内容与持久大文件分离，可用文件引用按需读取。

5.3 在模型真正可见的边界交付

普通消息随下一工具返回或批次边界一次附带。投递成功表示扩展已接收；交付则表示消息已进入模型可见上下文。缓存只在选定交付路径确实进入模型上下文后才完成交付，防止丢失或重复。

Pi 集成使用顶层 tool_result 附带消息，也在 turn_end 写入普通的 custom_message，供下一自然请求读取。紧急状态可以请求续轮；实际集成路径见 docs/INTEGRATION.md。codemode 可过滤内部工具返回，独立投递的收件箱消息在外层模型可见边界交付。[S2]

自动吃饭一类长期能力只需注册一次，此后由普通代码自行响应状态。代码可以使用函数、事件、循环、定时器、Promise、共享状态或自选库。全部游戏逻辑用普通 JavaScript 自由组合，内部协调由参赛代码处理。

6 等待返回与外部任务寿命

6.1 最小运行语义

确定方向：一次工具等待的寿命与真实外部任务的寿命分开。平台只需最小的运行、等待、取消和消息投递能力，允许模型把工作留在普通进程中。任务句柄只用于追踪运行和结果。

情形 | 当前工具返回 | 真实任务与后续结果

正常完成 | 任务结果，附带该边界应交付的收件箱消息。 | 任务结束；结果只交付一次。

请求提前判断 | running 状态、taskId、返回原因及消息。 | 只结束此次等待，目标任务继续运行。

后台任务随后完成 | 若有有效 wait，由该 wait 返回结果。 | 没有 wait 时进入收件箱，随下一工具返回交付。

明确取消任务 | 确认取消状态或说明失败原因。 | 实际停止目标；与“只结束等待”严格区分。



一个工具调用只有一个终结结果。提前返回后的最终完成结果通过新的 wait 或收件箱交付。任务完成与 wait 注册竞态时，也应只由一条路径消费完成结果。取消是否终止子进程树、保留何种日志，需要明确而简洁的执行约定。

建议返回对象包含 taskId、status、reason、可选 result 和 inbox。status 至少区分 running、completed、failed 与 cancelled。wait 关联同一 taskId；cancel 明确作用于真实任务。执行器维护最小任务状态和结果交付标记，保障完成结果只被一条路径消费。

6.2 需要执行器配合

提前返回需要执行器配合：它将目标进程、输出接管和最终结果保留在后台，并把当前等待释放给模型。这里应释放等待句柄并保留目标进程。原生 Pi 的 bash abort 会终止执行 [S3]；当前项目扩展的 abort 仅脱离等待，task_cancel 或执行 timeout 才终止进程。如果同一 assistant 批次中还有其他阻塞工具，仅释放其中一个仍可能拖住下一次模型调用。

当前实现已覆盖受管 bash/task_wait 的整批等待释放、codemode 内外层交付和后台任务记录，并测试退出、超时与关闭清理。任务所有权及未交付收件箱数据保存在内存，重启恢复留待后续扩展。真实部署的紧急信息延迟仍需测量；具体测试见 docs/INTEGRATION.md。

6.3 场景验收示例

agent 启动一段施工程序，同时注册自动吃饭。程序自行处理材料统计和进食时机。施工进度、吃过一次食物等低优先信息按 key 聚合，不逐条打断；施工完成时，结果和当时的聚合消息一次返回。

若食物不足而需要更高层决策，程序投递原因并请求提前判断。等待工具返回 running、taskId 和当前情况，施工目标进程继续存在。模型可决定补给、修改代码或显式取消施工。原施工随后结束时，由有效 wait 接收结果；没有 wait 则暂存，随下一工具返回交付一次。

该例说明交付机制。模型也可以预先编写自救策略，让代码自行处理食物不足。是否停工、是否换路、是否给队友发消息，仍由参赛代码与模型决定。

7 模型费用速率与运行资源

7.1 官方报价与现金速率窗口

所有参赛模型请求经过容器外网关，主模型、子代理、摘要和重试共用个人及队伍计量。运营者按模型配置官方 API 报价，记录来源、核对日期、币种，以及每百万未缓存输入、缓存输入和输出 token 的价格；网关据此折算参考成本。CPU、内存、磁盘、进程数和网络额度另行配置。

现金策略按时间窗口控制调用速率。请求派发前按输入估算和输出上限预留参考成本，再按供应商 usage 结算；缓存明细或 usage 缺失时标注估算、部分或未知状态。个人和队伍的窗口速率共同约束准入，窗口拥堵时排队，单次请求超过整个窗口容量时要求缩小请求。预留压力与已结算成本分别表达。

旧 token TPM 与并发限制可保留为技术兼容。累计 token 限额可用 tokens: null 关闭；现金策略的目标是速率控制，累计总额由运营者监控并决定何时结束比赛。当前字段、默认值和实现限制见 packages/budget-gateway/README.md；新增行为的测试证据见验证报告。

7.2 模型可见反馈与排队

模型获得当前窗口的未缓存输入、缓存输入和输出成本占比，窗口负载与等待前的超速比例，以及实际排队延迟。超速比例描述现金速率压力；预留与结算状态、估算质量随反馈标明。具体金额、币种、单价和累计总额留在运营端。按用途归因须有可靠标签，计费项目占比直接依据可用 usage。

比例反馈在自然工具或回合边界交付，保持简短、去重，不额外触发模型请求。模型限速排队时，Minecraft 墙钟、普通脚本与插件继续推进。已组装请求排队后收到的新消息，按下一模型可见边界交付；实际排队时间和游戏进展共同影响后续决策。

7.3 运营端累计成本与结束控制

运营端保存每次调用的 usage、计价质量和具体参考金额，汇总个人、队伍与全场累计成本。此金额按官方 API 标价折算，用于比较和运营监控；实际账单须结合供应商计费方式核对。累计总额的监控阈值和关服、终止游戏由运营者掌握，并在比赛规则中明确。

当前网关连接 API 凭证式 chat/completions 上游。OAuth 属于原生 Pi 的能力，当前网关尚未接入；订阅或 OAuth 用量的实际成本应按相应服务核对。价格、窗口、异常 usage 和结束控制在目标部署中验收，比赛配置与运营结果一并保存。

8 视觉材料与使用引导

8.1 面向判断的视觉输出

提供现成、快速的大面积俯视小地图和 Mineflayer 3D 渲染。模型拿到裸图，说明另附，包括视角、范围、比例或坐标、采样时间、图例与已知信息限制。世界镜像数据可按需读取；图像、原始可用状态与辅助统计一并作为 agent 自主判断的材料。

渲染操作应能放进模型已有脚本：请求或取得图像路径后，在同一脚本内读取图像并返回，避免为机械取图额外占一轮模型判断。图像生成延迟、可用范围与视觉编码成本需要实测，并与比赛能力配置一起公布。

8.2 短说明与可运行示例

常驻能力说明保持短小：告诉模型如何读取资料、启动普通代码、获得游戏状态、加载插件，以及消息在什么边界交付。详细技能材料提供可运行示例和接口差异，队内 Git 保存一致版本的工具和插件源码。示例必须与实际环境版本一起验证。

施工加自动吃饭：演示一个程序内普通并发、状态共享、低优先事件聚合，以及何时请求提前判断。

渲染并读取：演示在同一脚本中获得和读取图像；可选择只返回有用区域或一次组合多项观察。

后台完成交付：演示提前结束等待、后续 wait 与收件箱互斥交付，以及显式取消真实任务。

教学重点是把可程序化的筛选、合并和投递留在代码中，并理解工具返回边界。已有并行工具能力可直接使用，agent 自行决定执行节奏和重新判断时机。

8.3 可选反馈实验

进阶实验可对重复失败、无变化轮询、长时间只造工具却无游戏进展给出反馈。反馈需附具体证据，设置冷却和去重，随工具返回交付；并清楚标明它是启发式建议。此项放在基本回路验证之后。

比较无提示、短指南、短指南加反馈三种条件，保持地图、现金速率窗口和运行资源一致。运营端观察模型轮次、输入输出与缓存 token、官方标价参考成本、墙钟、游戏进展和胜负。少工具调用不等于少模型请求，少模型轮次也不保证成本更低。手操 baseline 先在确实可比的局部任务中实测。

9 最小实现范围与验收

9.1 推进顺序

第一步先打通基本闭环：一张固定地图、一个 bot、Pi、普通游戏程序、少量获准动作、状态镜像、外部模型网关与可信结束判定。此时即可观察 agent 是否能持续获得状态、行动并完成一段真实游戏目标。

第二步验证选定插件、自定义 Goal 和 Movements、长期普通程序、视觉输出，以及收件箱和等待分离。把兼容差异与返回语义固化成小型回归用例。第三步再做队伍协作、全场对局与统一指标；启发式反馈作为后续实验，不阻塞基本可玩性。

9.2 仓库与交付结构

仓库采用 Node 24 与 ESM，按职责划分模块并保留统一入口。建议结构如下；模块内部组织可随实现调整。交付提供安装与启动说明、示例配置、测试命令和已验证范围，打包为一个可解压使用的项目。

模块 | 职责

inbox 与 pi-extension | 本地投递 IPC、消息缓存、Pi 返回边界与执行等待集成。

mf-bridge 与 bot-sdk | 可信 Mineflayer 后端、语义桥接、容器内 facade、镜像及插件适配。

arena 与 budget-gateway | 比赛生命周期、规则与结果、外部模型参考成本计量和限速。

world-visual | 俯视小地图、3D 渲染、图像与说明输出。

infra | 容器、网络边界、部署与运行环境配置。



9.3 首版通过条件

验收项 | 通过证据

协议边界 | 参赛容器可完成允许动作；尝试直连或发任意协议包不能绕过后端；可信凭证不可由参赛环境取得。

插件与自定义扩展 | 选定 Pathfinder 和 PvP 的典型路径可运行；自定义 Goal 与 Movements 可在本地执行；同步寻路没有逐节点 RPC。

长期普通程序 | 一次注册后自动行为持续工作；与另一段游戏逻辑并行运行；模型限速等待时程序仍按规则执行。

镜像与时序 | 实体引用、位置更新、区块未知态、停止与 physicsTick 相关行为有可复现测试；记录实际事件延迟。

聚合与可见性 | 追加事件与按 key 覆盖按预期工作；消息在模型可见的返回边界出现；codemode 过滤不造成提前清空。

提前判断 | 请求提前判断能释放等待并交付原因；目标进程继续运行；覆盖同批多个阻塞工具。

完成一次交付 | 提前返回后的任务完成，仅通过有效 wait 或收件箱一条路径交付；覆盖完成与 wait 同时发生的竞态。

速率与墙钟 | 并发、子代理、重试和摘要纳入计量；模型可见窗口成本占比、超速比例及排队延迟，具体金额留在运营端；排队期间游戏与脚本按规则继续。

视觉与说明 | 小地图和 3D 图可读取，说明与图像一致；能在同一脚本取图并返回；引导示例在固定环境跑通。

全场比赛 | 从准备、开局到结束和结果完整跑通；地图目标与裁判一致；可复核胜负、关键异常与消耗。



9.4 必要日志与失败定位

建议记录对局和环境版本、模型请求与用量、工具及任务标识、语义动作结果、关键状态事件、消息交付边界、网关排队及裁判结束原因。日志用于复核能力边界、计量、重复交付和兼容故障。

对失败至少区分参赛代码错误、模型策略失败、接口不支持、状态过期、插件适配问题和服务故障。影响公平的异常依据赛前约定处理。日志保留期限、可见范围和选手赛后可获得的材料仍待决策。
