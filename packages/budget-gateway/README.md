# Trusted model budget gateway

Node HTTP OpenAI-compatible chat/completions proxy. Launch `node packages/budget-gateway/src/cli.mjs infra/budget.cash.example.json` after explicitly choosing a model, filling per-window cash rates, and configuring real model IDs and environment names. Client calls trigger model requests. Tests use a local fake upstream.

The budget file names one public `modelConfig` JSON, resolved relative to it. The gateway and participant both read that same operator-owned, read-only file: model ID, protocol, context/compaction metadata, output default and generation timeout. The budget file contains only account/rate settings, estimation settings and trusted upstream routing. Public model files contain no credentials or prices. Edit `infra/model.example.json`, or Windows `model.codex.json` / `model.deepseek.json`, rather than repeating model limits across services. The generic GPT-4.1 descriptor advertises the pinned provider catalogue’s 1,047,576-token context and 32,768-token output capacity; explicit account budgets remain separate operator settings.

Client base URL: `http://budget-gateway:8081/participants/red1/v1`; bearer token maps to that one server-configured participant. Main agent, scripts and subagents **must all use that same gateway identity**. Only gateway receives upstream key. Participant network must deny external provider access; network isolation enforces this route.

Participant/team concurrency reservations and optional lifetime token/rolling 60-second TPM policies are acquired atomically before upstream dispatch. `tokens:null` disables the cumulative token cutoff and `tpm:null` disables token-rate admission. Cash configurations use both nulls: the cash debt queue owns rate control, so a large valid context does not hit a second permanent token-size rejection. Queued cancellation does not charge. In-flight reservations do not expire; settlement starts their rolling window, conservatively limiting overlap. FIFO applies within shared accounts; independent teams can progress. In the optional token-only examples, a request larger than the explicitly configured account TPM is rejected at admission. Total budget counts reserved tokens, so an exhausted request may be rejected while earlier calls still await refunds; caller may retry after settlement.

Actual OpenAI usage settles/refunds both accounts exactly once. A definite HTTP rejection without usage releases token and cash reservations. Accepted generation followed by missing usage (disconnect/malformed usage) retains the full reservation. Native adapters distinguish these cases through trusted rejection metadata, stripped before participant delivery. If actual usage exceeds reservation, overspend is recorded, remaining budget is clamped to zero, and subsequent requests are blocked when insufficient; estimator error cannot provide a strict prepaid hard cap. For strict accounting, install a verified tokenizer/model-specific usage adapter and validate reasoning/cached token semantics with the provider. SSE `stream_options.include_usage` is forced. In token-only compatibility mode raw stream bytes are forwarded; cash mode re-encodes SSE JSON to strip provider monetary extensions while preserving choices and token usage; final usage chunks split across TCP boundaries are understood. Nonstream responses supported. Provider request fields, message/content formats, client tool choices and media are passed through. Hosted/server-executed tools (including `web_search_options`) remain unavailable because their actions and extra charges are outside this ledger. Completion storage is forced off and caller-selected user attribution is removed on the shared provider account. The gateway does not duplicate the provider's schema, decode image files, parse opaque reasoning signatures or reject remote image references. It never fetches those references itself. Each image reserves configurable `imageTokenAllowance` (default 4096); encoded image data is omitted from text estimation. Other content is counted as serialized input. The allowance is approximate and actual provider usage remains authoritative. Positive integer output and choice counts are required for accounting; `n` reserves output for every requested completion. The OpenAI-compatible route supports /chat/completions; a configured Pi-native upstream uses /messages. Raw Responses API is not exposed.

The default estimator reserves UTF-8 JSON bytes plus 256 overhead plus requested output (or the model descriptor default); `estimator:'approximate'` instead divides by 4 and is less conservative. Both estimates are approximate. Feedback travels in response headers: queue delay is in `x-arena-queue-delay-ms`, reservation in `x-arena-reserved-tokens`; trusted client integration may read these and steer its NEXT request, whose content is then estimated/reserved. Configured cash mode also meters official API list-price reference cost and queues against participant/team cash-per-window rates.

Single process, in-memory match ledger. **Do not restart during a match or run multiple replicas**: restart loses budget state. Production needs durable atomic state, bounded queue/admission rate limits, structured failure metrics, gateway readiness checks, and host-controlled egress restrictions. The operator supplies token credentials and configuration. Keep gateway logs/config out of participant mounts. Upstream HTTP is acceptable only for local tests; production should use an operator-verified HTTPS endpoint.

## Model-visible feedback transport

Authenticated `GET /participants/{id}/v1/budget` uses the same scoped bearer and reports `{participantId,teamId,at,participant,team,lastRequest}`. Each account includes lifetime limits, reservedTokens, settledTokens, usedTokens (settled + reserved), remainingTokens, overrunTokens, active and rollingTokens. No upstream request or token charge occurs. lastRequest records the last admitted queueDelayMs/reservedTokens/admittedAt. The endpoint is scoped to the authenticated participant and its team's aggregate.

Response headers `x-arena-participant-remaining-tokens` and `x-arena-team-remaining-tokens` are admission-time snapshots after reserving this call, not final actual usage. Pi's trusted response hook can make these visible in the next tool/context update without another model call; a single optional budget read after completion gives settled state. Queue delay measures elapsed milliseconds. Integrations deliver feedback in a subsequent request, which receives its own estimation and reservation.

Live CLI configuration may set requireRunningMatch:true plus each participant matchStatusUrl and matchTokenEnv. The operator-provided bridge token stays in trusted services. Before queueing and again after acquiring a reservation, the gateway fetches authenticated match state with a two-second timeout and permits only running. Failure or ended state denies admission; a reservation that never dispatches is fully refunded. Already-dispatched provider calls are not cancelled by a later end and still settle against the budget. The live Compose template enables this guard; standalone configuration does not.

## Context feedback and reservation accounting

The provider owns actual context limits. The gateway estimates input as JSON bytes / 4 plus framing and image allowances for feedback and cash quotes. It does not reject a request against a guessed context window. Pi uses the shared descriptor's context and compaction metadata to manage history.

`estimator:'conservative'` reserves one token-budget unit per JSON byte plus framing/images/output; `estimator:'approximate'` uses bytes / 4. Both are estimates, and provider usage settles them. Explicit numeric token/TPM policies and account concurrency remain available as admission boundaries; there is no second `maxReservationTokens` cap. An explicit requested output can exceed the descriptor's default, subject to the account budget and provider capability. `x-arena-estimated-context-tokens` and `x-arena-reserved-tokens` expose the two estimates separately.

## Official-price cash-rate mode (default operator path)

`infra/budget.cash.example.json` and `budget.cash.live.example.json` contain an **illustrative**, verified GPT-4.1 price entry: USD 2 / 0.5 / 8 per million uncached-input / cached-input / output tokens. Sources: https://developers.openai.com/api/docs/models/gpt-4.1 and https://openai.com/index/gpt-4-1/ (verified 2026-10-10). These are official API list-price **reference costs**, not actual invoices, payments, subscription usage charges or a model choice made for the user. The operator must choose/freeze the actual model and its rates; Subscription OAuth uses the [trusted Pi Codex adapter](../codex-adapter/README.md) and its native Pi endpoint.

Configure `referenceCost:{mode:'official-api-list-price',currency,windowMs,models:{MODEL:{provider,inputPerMillion,cachedInputPerMillion,outputPerMillion,sourceUrl,verifiedAt}}}`. Rates are decimal strings in currency per million tokens. Every allowed model must have usable numeric rates or cash mode fails startup. Source/provider/date fields document the operator’s price selection; they are not runtime validation gates. Each participant/team needs `cashRateLimit` as a positive decimal currency amount **per window**, not a lifetime allocation. Example amounts are intentionally unset; startup rejects placeholders. Price entries are static per match and must be reviewed when the operator changes model/provider/pricing tier.

Money uses integer pico-currency units (10^-12); per-million rates support six decimal places. Rate windows must fit the exact integer range (up to 9007.199254740991 currency units per window). Lifetime operator accumulation uses BigInt. Cash quotes use the approximate context-input estimate, separately from conservative token safety units, plus maximum output. Optional model longContext rates apply above their thresholdTokens; quotes use estimated input and settlement uses actual prompt_tokens. Input cached tokens are subtracted from prompt_tokens; completion reasoning tokens are already part of output and never charged a second time.

Requests obtain concurrency admission and cash-window admission. The token ledger still records usage but shipped cash configurations disable its cumulative and TPM cutoffs. Its concurrency reservation is acquired first and remains held while cash admission queues, so this serial acquisition is conservative. Participant/team admissions are atomic within each ledger. Cancellation, token rejection, cash rejection, and match-end rejection before upstream dispatch refund all acquired reservations. Cash admission uses a debt bucket: when existing debt plus in-flight holds is below one window allowance, a request may enter even if its quote is larger than that allowance. Its in-flight hold is capped at one allowance; actual settlement replaces the hold with full debt. Debt drains continuously at cashRateLimit/windowMs, so large actual costs delay later requests across multiple windows. Refunds release waiting requests immediately. Shared-team FIFO and concurrency limits still apply; token-only rolling TPM semantics are unchanged.

Actual prompt/completion/cache details settle the official-price reference cost. Missing cached-token detail yields an explicitly estimated uncached-input upper-cost assumption. Total-only or absent usage is unknown: its full cash reservation remains charged to the rate window, with no invented input/output split. Unknown reservation estimates remain separate from priced usage in the operator account. Invalid excessive provider reports stop further cash admission if they exceed exact supported rate arithmetic. None of this claims an exact provider invoice.

### Ratio-only participant view

`x-arena-cash-ratios` contains JSON `{participant,team}`. GET /v1/budget exposes the same objects as participant.cash/team.cash:
- basis: official-api-list-price-reference; coverage: current-window-priced-usage-only
- costShare: uncachedInput, cachedInput, output fractions of currently settled, priceable reference cost; null when unavailable. No pending reservation is fabricated into a billing category.
- quality: exact / estimated / partial / unknown / no-usage; calls: priced / estimated / unknown counts within the current window
- rate.windowMs; rate.windowLoadRatio = current settled-plus-inflight cash occupancy / window allowance
- rate.overRateRatioBeforeWait = max((occupancy at initial queue entry + this request's cash reservation - window allowance) / allowance, 0)
- rate.queueDelayMs = actual combined token-and-cash admission wait for the request
- enforcement: cash-rate-queue

These are rate pressures, **not cumulative-budget overspending**. A value 0.2 means 20%; pressure can exist while a request waits even though its eventual settled usage is much smaller. Headers are admission-time snapshots; one authenticated read at a natural post-response boundary refreshes settled shares without another model call. Large cash requests queue instead of producing a permanent size-based 429. Participant responses expose no cash amount, rate table, currency, cumulative reference cost or cumulative target ratio. Cash mode strips provider response/usage monetary extension fields; token usage is retained. Pricing metadata and operator logs must stay outside participant volumes/environment.

### Operator totals and ending a match

`cashLedger.operatorSnapshot(id)` and trusted `onMetric.referenceCost` contain cumulative decimal reference costs, per-category amounts and separately labelled unknown-usage reservation estimates. The operator monitors these totals. No new cumulative-money cutoff is implemented. `tokens:null` and `tpm:null` disable separate cumulative/token-rate cutoffs. Numeric token limits remain an optional legacy policy and only stop model admission, not the game.

To end gameplay under operator supervision, send SIGTERM/SIGINT to the trusted arena-host (e.g. `docker compose --env-file .env -f infra/compose.live.yaml kill -s SIGTERM arena-host`); its implemented graceful end path gates actions, clears controls, runs configured end commands and disconnects game bots. Inspect result/stopConfirmed, then stop participant/gateway services. If a hard process kill bypasses the graceful handler, it is not evidence that configured game cleanup completed. Cash admission alone does not authorize remote shutdown or financial transactions.


Body and SSE-line size limits are optional operator transport policies (maxBodyBytes and maxSseLineBytes), independent of model context tokens. With no explicit policy, the gateway adds no default byte ceiling; valid image history and native terminal blocks can exceed the old 8 MiB body / 2 MB event sizes. The trusted adapter likewise applies a body ceiling only when configured.
