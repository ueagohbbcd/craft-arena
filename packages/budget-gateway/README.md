# Trusted model budget gateway

Node HTTP OpenAI-compatible chat/completions proxy. Launch `node packages/budget-gateway/src/cli.mjs infra/budget.cash.example.json` after explicitly choosing a model, filling per-window cash rates, and configuring real model IDs and environment names. Client calls trigger model requests. Tests use a local fake upstream.

Client base URL: `http://budget-gateway:8081/participants/red1/v1`; bearer token maps to that one server-configured participant. Main agent, scripts and subagents **must all use that same gateway identity**. Only gateway receives upstream key. Participant network must deny external provider access; network isolation enforces this route.

Participant and team lifetime token budgets, rolling 60-second TPM and concurrency reservations are acquired atomically before upstream dispatch. Queued cancellation does not charge. In-flight reservations do not expire; settlement starts their rolling window, conservatively limiting overlap. FIFO applies within shared accounts; independent teams can progress. A request larger than account TPM is rejected at admission. Total budget counts reserved tokens, so an exhausted request may be rejected while earlier calls still await refunds; caller may retry after settlement.

Actual OpenAI usage settles/refunds both accounts exactly once. Missing usage (upstream failure/disconnect/malformed usage) charges full reserved tokens, so retries remain budgeted. If actual usage exceeds reservation, overspend is recorded, remaining budget is clamped to zero, and subsequent requests are blocked when insufficient; estimator error cannot provide a strict prepaid hard cap. For strict accounting, install a verified tokenizer/model-specific usage adapter and validate reasoning/cached token semantics with the provider. SSE `stream_options.include_usage` is forced. In token-only compatibility mode raw stream bytes are forwarded; cash mode re-encodes SSE JSON to strip provider monetary extensions while preserving choices and token usage; final usage chunks split across TCP boundaries are understood. Nonstream responses supported. Text content arrays and inline PNG/JPEG image_url blocks are supported; remote image URLs, audio, other content types, n>1, and unknown request fields are rejected. Inline image headers, bytes, dimensions and counts are bounded; validation covers image headers and encoded payload bounds; full decoding belongs to the image consumer. Image base64 bytes are excluded from text estimation and each image reserves configurable imageTokenAllowance (default 4096); operators must verify this allowance against their selected provider/model/resolution. The allowance is approximate and must cover reasoning/image token behavior. The OpenAI-compatible route supports /chat/completions; a configured Pi-native upstream uses /messages. Raw Responses API is not exposed.

The default estimator reserves UTF-8 JSON bytes plus 256 overhead plus configured output cap; `estimator:'approximate'` instead divides by 4 and is less conservative. Both estimates are approximate. Feedback travels in response headers: queue delay is in `x-arena-queue-delay-ms`, reservation in `x-arena-reserved-tokens`; trusted client integration may read these and steer its NEXT request, whose content is then estimated/reserved. Configured cash mode also meters official API list-price reference cost and queues against participant/team cash-per-window rates.

Single process, in-memory match ledger. **Do not restart during a match or run multiple replicas**: restart loses budget state. Production needs durable atomic state, bounded queue/admission rate limits, structured failure metrics, gateway readiness checks, and host-controlled egress restrictions. The operator supplies token credentials and configuration. Keep gateway logs/config out of participant mounts. Upstream HTTP is acceptable only for local tests; production should use an operator-verified HTTPS endpoint.

## Model-visible feedback transport

Authenticated `GET /participants/{id}/v1/budget` uses the same scoped bearer and reports `{participantId,teamId,at,participant,team,lastRequest}`. Each account includes lifetime limits, reservedTokens, settledTokens, usedTokens (settled + reserved), remainingTokens, overrunTokens, active and rollingTokens. No upstream request or token charge occurs. lastRequest records the last admitted queueDelayMs/reservedTokens/admittedAt. The endpoint is scoped to the authenticated participant and its team's aggregate.

Response headers `x-arena-participant-remaining-tokens` and `x-arena-team-remaining-tokens` are admission-time snapshots after reserving this call, not final actual usage. Pi's trusted response hook can make these visible in the next tool/context update without another model call; a single optional budget read after completion gives settled state. Queue delay measures elapsed milliseconds. Integrations deliver feedback in a subsequent request, which receives its own estimation and reservation.

Live CLI configuration may set requireRunningMatch:true plus each participant matchStatusUrl and matchTokenEnv. The operator-provided bridge token stays in trusted services. Before queueing and again after acquiring a reservation, the gateway fetches authenticated match state with a two-second timeout and permits only running. Failure or ended state denies admission; a reservation that never dispatches is fully refunded. Already-dispatched provider calls are not cancelled by a later end and still settle against the budget. The live Compose template enables this guard; standalone configuration does not.

## Context fitting versus reservation accounting

Configure context admission and budget reservation separately:

- `contextWindowTokens` (default 32768) is the operator-declared provider/model context window. `contextBytesPerToken` (default 4) gives an **approximate** text-context heuristic over UTF-8 JSON bytes, plus 256 framing allowance, image allowance and requested output. Accuracy varies with non-English text, tools and provider framing. The upstream provider still enforces its actual context limit. `contextTokens` remains a legacy alias only.
- `estimator:'conservative'` reserves one token-budget unit per UTF-8 JSON byte (excluding encoded image bytes), plus framing/image allowances and output. This byte-based safety reservation is checked against the reservation cap; the separate context estimate is checked against the model context window. Actual provider usage settles/refunds the reservation.
- `maxReservationTokens` (default 131072 for the supplied 32768 window) bounds this safety reservation independently. Shipped participant TPM is 131072 and team TPM 262144, so a full allowed reservation fits; the cash examples set tokens:null, disabling cumulative token cutoff while retaining TPM/concurrency. Legacy token-only examples retain their explicit cumulative token caps. Concurrent large reservations may queue, and an account near exhaustion can reject a conservative reservation even when actual eventual usage might be smaller.

A 34800-byte ordinary text history can therefore fit the approximate 32768-token context window while reserving over 32768 budget units. The `x-arena-estimated-context-tokens` response header exposes the approximate context estimate separately from `x-arena-reserved-tokens`. Neither heuristic guarantees exact context fit or a mathematically strict upper bound on provider usage; use a verified tokenizer and model-specific vision/reasoning adapter when those guarantees matter. Pi compaction uses its own token estimates and configured headroom, and its summarization calls travel through this same gateway and budget.

## Official-price cash-rate mode (default operator path)

`infra/budget.cash.example.json` and `budget.cash.live.example.json` contain an **illustrative**, verified GPT-4.1 price entry: USD 2 / 0.5 / 8 per million uncached-input / cached-input / output tokens. Sources: https://developers.openai.com/api/docs/models/gpt-4.1 and https://openai.com/index/gpt-4-1/ (verified 2026-10-10). These are official API list-price **reference costs**, not actual invoices, payments, subscription usage charges or a model choice made for the user. The operator must choose/freeze the actual model and its rates; Subscription OAuth uses the [trusted Pi Codex adapter](../codex-adapter/README.md) and its native Pi endpoint.

Configure `referenceCost:{mode:'official-api-list-price',currency,windowMs,models:{MODEL:{provider,inputPerMillion,cachedInputPerMillion,outputPerMillion,sourceUrl,verifiedAt}}}`. Rates are decimal strings in currency per million tokens. Every allowed model must have complete metadata/rates or cash mode fails startup. Each participant/team needs `cashRateLimit` as a positive decimal currency amount **per window**, not a lifetime allocation. Example amounts are intentionally unset; startup rejects placeholders. Price entries are static per match and must be reviewed when the operator changes model/provider/pricing tier.

Money uses integer pico-currency units (10^-12); per-million rates support six decimal places. Rate windows must fit the exact integer range (up to 9007.199254740991 currency units per window). Lifetime operator accumulation uses BigInt. Price reservations use the configured input safety estimate charged at uncached-input rate plus maximum output. Input cached tokens are subtracted from prompt_tokens; completion reasoning tokens are already part of output and never charged a second time.

Requests must obtain both token TPM/concurrency and cash-window admission. The token reservation is acquired first and remains held while cash admission queues, so this serial acquisition is conservative. Participant/team admissions are atomic within each ledger. Cancellation, token rejection, cash rejection, and match-end rejection before upstream dispatch refund all acquired reservations. In-flight reservations remain occupied until settlement; settled usage remains in the rolling window for windowMs from settlement. Partial usage refunds can admit waiting requests. A single cash reservation larger than the whole window cannot become admissible merely by waiting: HTTP 429 returns safe ratio feedback and asks the caller to shrink context/output or have the operator revise the published rate.

Actual prompt/completion/cache details settle the official-price reference cost. Missing cached-token detail yields an explicitly estimated uncached-input upper-cost assumption. Total-only or absent usage is unknown: its full cash reservation remains charged to the rate window, with no invented input/output split. Unknown reservation estimates remain separate from priced usage in the operator account. Invalid excessive provider reports stop further cash admission if they exceed exact supported rate arithmetic. None of this claims an exact provider invoice.

### Ratio-only participant view

`x-arena-cash-ratios` contains JSON `{participant,team}`. GET /v1/budget exposes the same objects as participant.cash/team.cash:
- basis: official-api-list-price-reference; coverage: current-window-priced-usage-only
- costShare: uncachedInput, cachedInput, output fractions of currently settled, priceable reference cost; null when unavailable. No pending reservation is fabricated into a billing category.
- quality: exact / estimated / partial / unknown / no-usage; calls: priced / estimated / unknown counts within the current window
- rate.windowMs; rate.windowLoadRatio = current settled-plus-inflight cash occupancy / window allowance
- rate.overRateRatioBeforeWait = max((occupancy at initial queue entry + this request's cash reservation - window allowance) / allowance, 0)
- rate.queueDelayMs = actual combined token-and-cash admission wait for the request
- enforcement: cash-rate-queue

These are rate pressures, **not cumulative-budget overspending**. A value 0.2 means 20%; pressure can exist while a request waits even though its eventual settled usage is much smaller. Headers are admission-time snapshots; one authenticated read at a natural post-response boundary refreshes settled shares without another model call. Oversized-request 429 responses include the same safe ratio header and error.cashRatios. Participant responses expose no cash amount, rate table, currency, cumulative reference cost or cumulative target ratio. Cash mode strips provider response/usage monetary extension fields; token usage is retained. Pricing metadata and operator logs must stay outside participant volumes/environment.

### Operator totals and ending a match

`cashLedger.operatorSnapshot(id)` and trusted `onMetric.referenceCost` contain cumulative decimal reference costs, per-category amounts and separately labelled unknown-usage reservation estimates. The operator monitors these totals. No new cumulative-money cutoff is implemented. `tokens:null` disables the older cumulative-token cutoff; explicit numeric token caps remain available for compatibility but only stop model admission and do not stop the game.

To end gameplay under operator supervision, send SIGTERM/SIGINT to the trusted arena-host (e.g. `docker compose --env-file .env -f infra/compose.live.yaml kill -s SIGTERM arena-host`); its implemented graceful end path gates actions, clears controls, runs configured end commands and disconnects game bots. Inspect result/stopConfirmed, then stop participant/gateway services. If a hard process kill bypasses the graceful handler, it is not evidence that configured game cleanup completed. Cash admission alone does not authorize remote shutdown or financial transactions.
