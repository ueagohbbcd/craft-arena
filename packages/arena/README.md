# Trusted match lifecycle

`src/index.mjs` exports `validateMatchConfig` and `MatchHost`. This module is the host library; the separate live-cli.mjs below provides the runnable server controller. Custom integrations supply a trusted connector with async `prepare(config, runId)`, `start(runId)`, `stop(runId)`. A real connector must reset and verify the selected map, gate actions until synchronized start, and stop participant actions at end. Prepare/start failures leave the preceding state; external side effects require operator reconciliation. Stop failures produce `stopConfirmed:false`.

Config requires id, game=`race-of-wool`, map `{id, version, sha256}`, durationMs, teams `[{id}]`, participants `[{id,team}]`, rules `{objectives:[id,...],winner:'first-team-all-objectives',onTimeout:'draw'|'most-objectives'}`, versions `{participantImage,bridge}`. The map hash is an operator declaration; this library does not verify installed world bytes. No proprietary map is bundled.

`prepare()` → `start()` → authenticated `ingest(event, eventToken)` → `end()` → `result()`. Events have unique id and runId; objective events include team and objective, death/disconnect events participant. Duplicate IDs are ignored. Events must come from a trusted server-side observer that verifies the actual map's placements/order/ownership, never the bot/participant. `end` is trusted-only. For event-driven sources, the first team to all configured objectives wins; optional unique highest objective count at timeout. For polling sources, trusted code calls `observe({teamId: {objectiveId: boolean, ...}, ...})` with the full round. The host atomically replaces current progress, records objective/objective-lost transitions, and judges all teams together. Repeated unchanged observations add no events. Every configured team/objective must have a boolean observation; a missing or non-boolean observation rejects the entire round before changing progress. Only configured goals are read. The live adapter never writes host progress or chooses a winner. There is no implicit score from chat or participant claims. Abandonment/map-fault are explicit trusted operator paths.

Call `checkTimeout()` regularly from event-driven integrations (e.g. a timer); ingest and observe also check elapsed time before accepting data. A batch received at or after the deadline ends the match without changing progress; timeout scoring uses the last accepted pre-deadline state. The library is single-process in-memory and has no recovery/durable event log. Export result JSON for auditing. Result includes map/version provenance, received authoritative events, death/disconnect counts and lifecycle times; model cost/CPU metrics must be merged from their actual trusted collectors.

`node packages/arena/src/cli.mjs validate config.json` checks config. `simulate config.json` drives a deterministic fake connector and synthetic objectives, labelled `simulation-no-minecraft`. Live map, Minecraft session, scoring integration and deployment require separate validation. For a configured live monument match, use the supplied RCON/Mineflayer runner described below and provide the operator's map/server configuration.

## Configurable live runner

`node packages/arena/src/live-cli.mjs infra/match.live.json result.json` runs the supplied live connector. Copy `infra/match.live.template.json`, then fill every map/protocol/image identifier, every goal coordinate/name, and reset/start/end commands plus expected RCON acknowledgement regex. Template goal coordinates are deliberately null and validation rejects them until supplied.

`live.mjs` connects to the operator's existing Minecraft server through private RCON, executes configured reset commands, spawns a trusted Mineflayer referee, verifies all goal chunks are known and all monuments initially incomplete, and spawns one action-gated bridge per participant. `live.observer.commands` can optionally contain the same `{command,expect}` pairs to position the referee after it has joined, e.g. operator-selected teleport/spectator commands. Server permissions, view distance and referee location must make **all goals simultaneously observable**; this adapter fails preparation if they remain unloaded. Distributed monument maps need a larger configured server view distance/suitable observer position or a future multi-observer extension.

The referee polls exact block names and optional block-state properties at configured monuments. Completing all objectives wins; unknown/unloaded blocks never score. This adapter fits maps where those monument placements are sufficient proof. It does not verify acquisition provenance, intermediate order, scoreboard-only rules or map-specific anti-cheat. Choose a compatible map/ruleset. An observer error/disconnect is a map fault; a participant disconnect records a metric then abandons the match; deaths are recorded. These policies are fixed for this adapter.

All action authorization callbacks consult live host state. Before start and after end, bridge actions are denied. End clears held controls, navigation, digging and item use, runs configured stop commands, then disconnects owned game bots/referee/RCON while retaining authenticated read-only bridge status endpoints. Cleanup tries every bot even after individual failures; failures remain visible as `stopConfirmed:false`.

For coordinated operator start, set `live.startSignalFile` (template `/control/start`). CLI prepares all bot connections and waits for that marker while bridge actions remain gated. After participant agents are ready, operator creates the marker. Stale markers are rejected at the next launch; remove them before the next match. Omitting it starts immediately after bot readiness, which does not establish agent/model readiness. Start time begins after server start-command acknowledgements. A 100 ms default poll checks goals and wall-clock timeout; the host advances the running match automatically.

`infra/compose.live.yaml` uses this orchestrator to manage bridge processes and configures the correct per-bot bridge ports. It is still an un-deployed template. RCON credentials only enter the trusted host; backend has no published ports. The live runner uses a built-in TCP RCON client with auth, bounded packet parsing, request IDs and a second empty-command fence to collect multi-packet responses; validate empty-command response compatibility with the chosen server implementation. Commands are trusted operator input. Operators prepare the server, RCON access, credentials, permissions and applicable agreement acceptance before launch.

Polling resolves observation time only, not exact placement time. If multiple teams first satisfy all goals in the same observation round, the live adapter records their objectives and ends with `simultaneous-objectives`, winner null, according to the shared observation round. This tie policy must be included in the operator's published rules. Games requiring sub-poll ordering need authoritative server event timestamps instead of this polling adapter.

The CLI atomically replaces its `RESULT.json` argument with the current run state (`created`, `prepared`, `running`, `ended`, or startup `failed`) and a fresh `runId`. Starting another run clears the previous winner/result immediately, even if config loading or preparation fails. On completion it first saves `runs/<runId>.json` beside the current file, preserving prior runs, then publishes the final current result with its relative `resultPath`. Bridge match status and CLI lifecycle output also include `runId`. These are plain JSON files, not crash recovery or a live event database. On natural completion live-cli.mjs remains available as a read-only status daemon until operator SIGINT/SIGTERM. This is deliberate: participants can still fetch authoritative ended after Minecraft connections have closed. Explicit runner.close() or CLI shutdown also closes status HTTP services. Admission checks in the live gateway reject model work unless this trusted status says running; in-flight calls already dispatched are settled normally.

Live monument progress tracks current state: each poll recomputes all configured goal blocks, records objective/objective-lost transitions, and uses current presence for win and timeout scoring. Losing chunk visibility during a running match ends it as map-fault to preserve scoring integrity. The event history remains available after removals.
